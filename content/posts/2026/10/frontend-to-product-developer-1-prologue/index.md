안녕하세요. 프론트엔드 개발자 윤해진입니다.

자기소개를 할 때면 늘 이렇게 말하곤 했어요. 그런데 요즘 제가 하는 일을 FE라고만 부르기엔 좀 애매해진 것 같아서, 스스로 한번 정리해보게 됐어요.

UI를 만들고 컴포넌트를 설계하는 건 기본이고, 어느 순간 Docker 파일을 들여다보고, Nginx 설정이 왜 이렇게 됐는지 뒤적이고, 서버 로그에서 에러를 추적하고 있었어요. DB 테이블을 열어 보면서 "이 값은 가져올 수 있겠다, 이건 구조를 손봐야 할 것 같은데" 같은 말을 기획자분께 드리기도 했고요.

**이 글에서는 제가 단독 FE로 리뉴얼 프로젝트를 맡게 된 배경과, 화면 밖 영역에 어떻게 들어가게 됐는지를 먼저 이야기해보려 해요.**

## 1. 입사하고 두 달, 리뉴얼 프로젝트가 시작됐어요

입사하고 두 달이 채 안 됐을 때 리뉴얼 프로젝트가 시작됐어요. B2C 서비스였는데, 다양한 기획이나 이벤트, 마케팅을 시도하려고 해도 기존 레거시 스택으로는 대응하기가 너무 어려운 상황이었거든요. 기능 하나 추가하려면 구조 자체를 건드려야 했고, 그게 반복되다 보니 결국 새로 만드는 쪽으로 결정됐어요.

기존 서비스는 MongoDB 기반이었는데, 스키마 없이 자유롭게 쌓인 데이터라 구조를 파악하는 일부터 쉽지 않았어요. FE도 EJS 템플릿 방식이라 Node.js 서버에서 HTML을 그대로 렌더링하는 구조였고, 컴포넌트나 상태 관리 개념이 없다 보니 인터랙션이 복잡해질수록 한계가 명확했어요. 확장하려면 구조를 통째로 뜯어야 하는 상황이었죠.

UI만 바꾸는 게 아니라 DB 설계부터 인프라 구성까지 전부 새로 만드는 작업이었어요. 그리고 **이 전 과정을 단독 FE로 진행하게 됐어요.**

## 2. 막히는 지점이 보이면 일단 제가 먼저 들어갔어요

### 서버 로그를 직접 열었어요

이슈가 생겼는데 백엔드(BE) 개발자분이 여유가 없을 때는, 서버 로그를 직접 열어서 원인을 파악했어요. 처음엔 로그를 어디서 찾아야 하는지, 어떻게 읽어야 하는지부터 막막했는데, 여기서 AI를 적절히 쓰니 생각보다 빠르게 감을 잡을 수 있었어요. 에러 내용과 발생 시점을 AI한테 넘기고 코드베이스랑 연결해서 찾아달라고 하면, 확실한 시점과 데이터가 있으니 원인을 꽤 정확하게 짚어주더라고요.

**클라이언트 로그만 보던 시야가 서버 로그를 직접 읽고 흐름을 추적하는 데까지 넓어진 게 꽤 큰 변화였어요.** 개발자끼리는 맥락을 공유하고 있으니까, 흐름을 짚어서 가져가면 바로 이야기가 통했어요.

### DB 테이블을 열어 놓고 기획 이야기를 했어요

기획, 운영 측과 개선 방향이나 새로운 피처 이야기를 할 때는 DB 테이블을 직접 열어봤어요. 이 값을 가져올 수 있는지, 지금 구조라면 개선 방향을 어떻게 잡아야 할지, 공수는 어느 정도 드는지를 같이 보면서 이야기하니 논의가 훨씬 구체적이 됐어요.

DB 구조를 들여다보다 보니 자연스럽게 FE 컴포넌트나 기능 설계에서도 더 많은 가능성이 보였어요. 어떤 데이터가 어떻게 흐르는지 알면, 화면을 어떻게 나눌지, 어디서 상태를 들고 있어야 할지도 더 선명하게 보이더라고요.

### 낯선 영역은 AI로 학습 허들을 낮췄어요

이런 변화에는 AI의 도움이 컸어요. DB 서버에 MCP(Model Context Protocol)를 연결해두고, 엔티티 구조나 테이블 간 관계를 AI한테 물어보면서 파악했어요. BE의 세부 흐름이나 인프라 개념을 익힐 때도 마찬가지였고요.

먼저 스스로 찾아보고, 제가 이해한 게 맞는지, 놓친 오류는 없는지 역으로 AI한테 물어보는 방식이 저한테 잘 맞았어요. 바쁜 일정 속에서도 이해도를 꽤 빠르게 끌어올릴 수 있었거든요.

> AI는 답을 대신 찾아주는 도구라기보다, 제가 이해한 게 맞는지 확인해주는 상대에 가까웠어요.

## 3. 이 시리즈는 그 과정을 기록해보려는 거예요

프론트엔드 개발자에서 프로덕트 개발자로 넘어가는 과정이에요. 잘한 것만 골라 남기기보다는, 그 과정에서 했던 고민까지 함께 담아보려 해요.

이런 분들이 읽으면 좋을 것 같아요.

- 작은 팀에서 FE 혼자 배포, DB, 기획까지 맡게 된 분
- Next.js와 React 중 무엇을 쓸지, 프로젝트 구조를 어떻게 잡을지 고민하는 분
- 배포나 DB가 아직 막연하게 느껴지는 FE 개발자
- 요구사항이 불명확할 때 기획, 운영과 어떻게 이야기를 맞춰가는지 궁금한 분

시리즈는 이렇게 이어져요.

1. **프롤로그: FE라고만 부르기 애매해졌어요** — 단독 FE로 리뉴얼 전 과정을 맡게 된 배경
2. **Next.js와 React를 나누고, FSD로 구조를 다시 잡다** — 서비스별 프레임워크 선택과, 개발 중반에 도메인 단위 구조로 바꾼 이야기
3. **서버와 인프라: FE가 Docker와 Nginx를 만진 이유** — PM2에서 Docker로, 그리고 Nginx로 요청을 나누기까지
4. **DB와 API 사이에서: 테이블을 보면서 기획을 다듬다** — DB 구조를 알고 나서 달라진 기획, API, 어드민 화면
5. **요구사항이 없을 때: 비즈니스부터 같이 파고들다** — 다른 직군과 같은 언어를 만들고 요구사항을 구체화한 과정
6. 서버 로그 추적과 에러 대응, 모니터링
7. 마무리 

다음 편에서는 리뉴얼을 시작하며 가장 먼저 정해야 했던 것, 기술 스택과 프로젝트 구조 이야기부터 해볼게요.
